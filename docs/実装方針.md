# 実装方針
更新日：2026-10-29。本人の最新指示に基づく正本。
この文書は旧docs/実装方針.txtおよび過去のLOCAL/DRIVE/移送指示に優先する。以前の移送指示2件は本人からCodexへ未送信。開始指示をdocs/CODEX_STAGE1.mdに一本化する。

## 目的
現実的な駆動・接触・局所センサに基づいてPiano-Moversの物体運搬を達成できるシミュレータを完成させる。その後のルール削減・寄与・効率・環境適応・故障等の比較検証を想定した実装にする。
シミュレーション内の整合性、実装可能なセンサの仮定、実機での実証を区別する。未実証を現実性確認済みとしない。

## 分担とレビュー
| 担当 | 責務 |
|---|---|
| Codex | 指示された段階のシミュレータ実装・修正・検証と、それに必要なGit操作・記録。研究目標や制約を独断で変更しない |
| ChatGPT | 目標の分割、方針・受入条件の整理、証拠と差分のレビュー、方針に沿うPRの承認判断 |
| 本人 | 研究意図と重要な選択の決定、各段階の結果をこのチャットへ提示 |
| GitHub | コード・方針・知見・実験記録・Issue/PRの正本。複数PCから復元可能にする |

各段階でCodexはPRと結果を提示して停止し、本人がこのチャットへ戻る。ChatGPTによる方針適合確認と次段階の明示的な開始指示を受けて進む。Codexの自己承認・自動マージ・次段階への自動進行は禁止。
段階内の小さい修正や必要検証のたびに承認待ちにする必要はない。完成前でも進捗をPR化できるが、マージと段階完了は別。部分PRの承認は未達条件を満たした意味ではない。
ChatGPTのレビューも誤り得るため、説明だけでなくコード差分・計測・再現手順を根拠にする。同じGitHubアカウントのPRは形式上自己承認できない場合がある。承認不可ならレビューコメントで判定と制約を明記し、別人による独立レビューと偽らない。

## 実装上の制約
- クラス・関数を過度に分割しない。クラス/関数定義・分岐・ループを深く入れ子にしすぎず、人間が追える構造にする。
- クラスの役割、関数の目的、複雑な処理の前提・理由をコメントする。必要な入出力・単位・座標系・副作用を明記する。
- マジックナンバーを埋め込まない。定数/設定に意味のある名前を付け、単位・根拠・調整対象かを記録する。
- 論理的根拠のない特例や、成功だけを目的とした救済を追加しない。
- 非現実的な行動や物理演算は禁止。荷物への特権的な力/トルク、ワープ、直接姿勢修正、全体経路・真値による個体制御を禁止する。
- 行動を意味のある単位で分離し、将来の比較では設定でON/OFFできる構造にする。独立性のために過剰なクラス階層を作らない。切替可能と採用済みは別。
- 基本はUNINFORMED/LEADER/FOLLOW。スライド由来の許容角・一定時間の状態維持を保持し、Codex独自追加は原則OFFで一覧化。逆押しは有用という経験を仮説として同条件のON/OFFで判断する。
- 記録はMarkdown（.md）。方針・知見・仕様対応・センサ仕様・実験結果をGitで版管理する。
- 各サービスの規約と利用制限を守る。旧アカウント/旧repoへ接続せず、認証制限を迂回しない。凍結原因やデータ消失を未確認のまま断定しない。
- クレジットと計算を浪費しない。既存成果を再利用し、方策/物理/高速化を一度に変更しない。長時間計算は仮説・予算・終了条件を定める。
- 物理dt/制御/センサ周期を維持して高速化する。衝突/監査を省略しない。独立試行の並列化と単一試行速度を区別する。
- 主2ファイルだけでなく補助/nativeソース・固定依存・設定・ビルド/実行手順を保存する。他OS未検証なら明記し、どのPCでも無条件に動くとは主張しない。
- 公開repoに認証情報や個人情報を入れない。巨大ログ・動画等は適切な成果物保存先を使い、原本/保全物を削除しない。

## 7段階と完了条件
| 段階 | 目標 | レビューへ持ち帰る証拠 |
|---|---|---|
| 1 現状確認 | 既存成果・コード版・方針との差・センサ仮定を棚卸しし新repoへ安全に移送 | 元/新SHA、主2本hash、依存/復元、既存結果の出典、仕様差、センサ一覧、未確認事項 |
| 2 旧版の再現・解析 | 成功実績のある原本を実行し、成功要因候補と時間尺度を調べる | 条件/seed、sim時間と実時間、動画と判定、補助処理の寄与候補、現行版の検証予算見積り。未再現なら条件と打切りを明記 |
| 3 スライドとの対応・実装 | 状態/観測/行動/遷移を対応付け、許容角・状態維持を含む仕様を実装 | スライド番号→仕様→関数の対応、独自追加一覧、単位、必要な状態遷移テスト |
| 4 力の観測・センサ確認 | 押す/掴む/逆押し/回転の力伝達と、局所センサが使えることを検証 | 下記のセンサ確認表、小ケースの入力→観測→指令→力→運動、欠測/遮蔽/遅延時の結果、物理との対応 |
| 5 運搬を妨げる原因調査 | 停滞・回転不足・状態偏り等を診断し、脱出方法の仮説を検討 | 直前ログ、比較条件、反証可能な仮説、単一要因の比較。新ルールの採用はChatGPT/本人と方針確認後 |
| 6 物体運搬成功の検証 | 元の問題で物体全体の到達を確認 | 固定SHA/条件、数値判定と成功動画、物理/局所性監査、未達/打切りも記録 |
| 7 再現性の確認 | 調整に使っていないseedで固定候補を評価 | 事前に決めた試行数/予算/判定、成功率と不確実性、時間分布、全結果、研究用基準版 |

各行の終了時に必ずこのチャットでレビューする。順序を変える/再現できない段階を先へ進める場合も黙って完了にせず、理由と次の範囲を確認する。
7段階の後に、最小ルール・各行動の寄与・効率・環境適応・故障等の研究検証を行う。成功実績は旧版と現実的現候補を分ける。600秒は成功の固定期限ではなく、過去5時間は実時間。

## センサ確認（段階1で棚卸し、段階3で契約、段階4で検証）
各観測について、次をdocs/SENSOR_SPEC.mdに記録する。
1. 何を、どの位置のどの機構で測るか。個体が現実に取得できる根拠と未実証の仮定。
2. 距離/視野角/遮蔽/検出対象/接触・把持時のみ有効か。出口方向も観測可能な情報に限定する。
3. 単位、座標系、符号、更新周期、遅延、ノイズ/分解能/飽和、欠測時の挙動。未モデル化をゼロ誤差実証としない。
4. 物理エンジン内部の真値から「センサを模擬する処理」と、controllerへ渡す観測の境界。欠測を真値で補わない。
5. 合力/全体位置/荷物全体速度は評価専用。個体制御に必要な接触力・運動は局所的に測定/推定できる範囲に制限する。
6. 既知入力で精度/符号/方向・境界を確認。接触/非接触、停止/回転、把持/解除、遮蔽/範囲外/欠測/遅延を必要な小ケースで検証する。
7. 力は指令値、実際の接触/把持反力、推定観測値を分ける。摩擦・質量・慣性・有限駆動/把持力・破断条件と整合させる。スカラー荷重と進行方向を妨げる成分を混同しない。

用語注意：「センサ視野角」とAGENT_ORIENT_RANGEは別。後者は過去資料では目的方向とのずれに応じた押す向きの許容角として使われる。本人が残すと指定した機能を、名称だけで別機能に置換しない。
STATE_CONTINATIONは必ず一定時間後に遷移する寿命ではなく、通常遷移を判定するまでの状態維持条件。フレーム値を秒と誤読しない。保持と停滞遷移の優先順も対応表へ残す。

## PR承認条件
- 対象段階・範囲・受入条件が明示され、最新方針との対応が説明されている。
- 差分と追加/削除/OFF処理、センサ/物理の仮定、定数の根拠が説明されている。
- 対象変更に必要な検証を実施し、実行済み・既存証拠引用・未実施を区別している。
- 人間が読める構造・クラス/関数コメント、再実行手順、Markdown記録を備える。
- 起動成功、物理/センサ検証、搬送成功、再現性を混同しない。証拠不足を成功扱いしない。
- ChatGPTが現物差分と証拠を確認して判定する。Codexは段階終了でPR URL/HEAD/結果/残課題を返して停止する。レビュー後にHEADが変わったら追加差分を再確認する。
